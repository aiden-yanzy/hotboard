### ⚠️ 六、重要更正（2026-10-19 全量跑批时发现，之前判断有误）

**更正 1：newsnow 从来没有被停用。**
`config.yml` 里 `engines.newsnow.base_url` 虽然是空串，但 `collect.py` 的 `load_config()` 会用
**环境变量覆盖**（`ENGINE_NEWSNOW_URL`），而 compose 的 `.env` 里写着 `ENGINE_NEWSNOW_URL=http://newsnow:4444`
→ **容器内生效的是这个地址**。2026-10-19 全量跑批实测：`newsnow: 源成功 15 失败 0 抓到 373 条`。
**此前"newsnow 已停用 / 那 15 个源没有数据 / 前端会显示空源"的说法是错的** —— 真相是：那 15 个源一直在正常采集。
（教训：判断"某引擎是否启用"必须看**容器内的实际配置**，不能只读宿主上的 `config.yml`。）

**更正 2：因此现在存在"双路重复采集"。**
P1 把 13 个 newsnow 独有源迁成 `custom` 之后，同一批站点会被采两遍：
```
custom:producthunt 50 条  +  newsnow:producthunt 30 条
custom:steam      100 条  +  newsnow:steam       30 条
custom:xueqiu      30 条  +  newsnow:xueqiu      30 条
…
```
`items` 的主键是 `(source_id, url_hash)`，两路的 `source_id` 不同 → **会落成两份条目** → 前端同一件事看两遍
（正是用户说的"不要两个并行"）。全量跑批：`新增 245 / 更新 2455 / 快照 2688`，其中一半是重复。

**处置（✅ 用户 2026-10-19 拍板"停"，已执行）**：对已迁成 `custom` 的 13 个站点，把 **newsnow 侧同名源 `enabled=false`**
（历史数据一行未删）。回滚脚本：`jobs/collector/sql/rollback-p1-newsnow-migrated.sql`（13 条 `enabled=true`）。
执行结果：

```
UPDATE 13
各引擎启用数：custom 13 / dailyhot 50 / newsnow 2      ← newsnow 只剩 zaobao、fastbull（未迁移的两个）
下一轮跑批：新增 20 / 更新 2365 / 快照 2373 / 错误 0
   custom  源成功 13  抓到 521 条
   dailyhot 源成功 50  抓到 1804 条
   newsnow  源成功 2   抓到 60 条                       ← 双路重复消失（上一轮"新增 245"降到"新增 20"）
```

**至此达成用户最初的目标：`custom` 成为唯一链路，不再"两个并行"。** `zaobao`（域名不可达）、`fastbull`（地理阻断）
暂留 newsnow 兜底；这两个解决后的收尾动作是停掉 `newsnow` 容器（引擎 `base_url` 置空即可，无需改代码）。

## 六、安全加固与 robots 影响面审计（2026-10-19）

### 6.1 加固内容（用户批准「都做」）
| 项 | 实现 | 位置 |
|---|---|---|
| **429/403 指数退避** | 源站限流时**不重试**（重试=加剧封锁），把源冷却：首轮 30 分钟、逐次翻倍、封顶 24h；冷却期该源本轮跳过且**不计错误** | `base.py`（`RateLimited`）+ `collect.py`（`source_backoff` 表 + 门禁）|
| **robots.txt 尊重** | 按域缓存源站 robots，Disallow 的 URL 直接跳过；取不到 robots 一律**放行**（fail-open） | `base.py`（`robots_allows`）+ 开关 `config.yml safety.respect_robots` |
| **robots 白名单例外** | 可对指定 `src_id` 显式开例外（写在配置里，**可审计**，不是偷偷绕过） | `config.yml safety.robots_allowlist` |

### 6.2 ⚠️ 审计结果：12 个源被 robots.txt 挡住（68 → 56）

| 被挡源 | 说明 |
|---|---|
| **知乎 / 快手 / B站 / 微博 / 腾讯新闻** | ⭐ **这 5 个是我们仅有的"有真热度"的源**（知乎 2885万、快手 1157万、B站 629万、微博 324万、腾讯 264万）|

原因：国内站 robots.txt 普遍 `Disallow: /`（主要针对搜索引擎），与"榜单聚合"无关。

**三个选项**（等用户拍板）：A 全遵守（56 源，当前状态）｜**B 高价值源列白名单（推荐，68 源）**｜C 全关 robots。

### 6.2.1 ✅ 用户决策（2026-10-19）：**选 C —— 全关 robots，回到 68 源**

```
safety:
  respect_robots: false        # 用户决策：覆盖优先
  robots_allowlist: []         # 仅在 respect_robots=true 时生效
```
- **决策依据**：国内站 robots 的 `Disallow: /` 主要针对搜索引擎爬虫；本项目只读**公开榜单**、
  只存**标题+链接+短摘要**（不转全文）、每源 **48 次/天**、不登录、不并发。
- **代价已知情**：开启时 68→56（丢知乎/快手/B站/微博/腾讯新闻等 12 个）。
- **永不丢失的退路**：robots 机制、白名单、影响面审计方法都**留在代码里**，
  想恢复合规只需把 `respect_robots` 改回 `true`（或只对这 12 个源用白名单做例外），**无需改代码**。

**C 生效验证（2026-10-19 16:48 实跑）**：
```

   custom: 源成功 68 失败 0 抓到 2488 条      ← 12 个源全部回归（last_err 清空）
```
真热度源回归实测：**知乎 3361 万 · 快手 1342 万 · B站 1030 万 · 腾讯新闻 278 万 · 微博 132 万**

### 6.3 本轮踩到的两个真坑（都已修 + 已写进技能库）
1. **dry-run 里 DDL 被跳过 → 后续 SQL 全崩**：`source_backoff` 只在 `not dry_run` 时建表 → dry-run 的 SELECT 报 `relation does not exist` → **事务进入 aborted** → 后面每条 SQL 都报 `InFailedSqlTransaction`（实测 dry-run 直接崩溃）。
   → 修：幂等 DDL **任何时候都执行**；异常分支**必须 `rollback()`**（Java/JS 同款"事务没回滚"坑）。
2. **robots 跳过被算成"错误"** → cron 脚本 `grep ❌` 会把合规跳过当成故障，**每 30 分钟误报微信**。
   → 修：单独计数 + 用 `🚫` 标记（与 `❌` 区分），summary 增 `robots_skipped` 字段。

## 七、展示层整理：源顺序 / 分类 / 名称 / 友链（2026-10-19，用户要求）

### 7.1 ⭐ 挖出一个长期存在的死代码 bug（排序一直没生效）
`apps/api/app/main.py` 里有一套"人工编排的默认顺序"：
```python
SOURCE_ORDER = ["zhihu", "weibo", ...]          # 用 src_id 建表
SRC_RANK = {name: i for i, name in enumerate(SOURCE_ORDER)}
out = sorted(..., key=lambda x: (SRC_RANK.get(x["name"], ...), x["name"]))
```
—— `SRC_RANK` 的键是 **src_id**（`zhihu`），却拿 **中文显示名**（`知乎`）去查 → **永远查不到** →
全部退化成"按中文名排序"（表现为 36氪/51CTO/AcFun/CSDN… 这种字母序）。
**修**：改为**以库里的 `sources.sort_order` 为准**（`sort_order` 成为默认顺序的唯一来源，用户可直接在库里调）。
