# 部署指南

> **部署只需要两个文件：`docker-compose.yml` + `.env`。**
> 镜像由 GitHub Actions 构建（amd64 + arm64 双架构）推到 GHCR，
> 服务器上**不需要源码、不需要 Node/Python、不需要构建**，`docker compose up -d` 即可。

**已实测的链路数据**（腾讯云北京 → ghcr.io）：

| 项 | 结果 |
|---|---|
| `docker pull` web 镜像（429MB） | **20 秒**（约 21MB/s） |
| 镜像架构自动选择 | ✅ 服务器拿到 `linux/amd64`，Mac 会拿到 `linux/arm64` |
| 部署目录最终内容 | 只有 `docker-compose.yml` + `.env` 两个文件 |
| 首次启动到站点可用 | 约 30 秒（采集器首轮自动建表 + 灌源） |

## 一、三分钟部署（推荐，任何人任何机器）

### 1. 装 Docker

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER && newgrp docker
```

国内拉基础镜像慢就配镜像站（`/etc/docker/daemon.json`）：

```json
{ "registry-mirrors": ["https://docker.1ms.run"] }
```

### 2. 只下载两个文件

```bash
mkdir -p /opt/hotboard && cd /opt/hotboard
curl -fsSLO https://raw.githubusercontent.com/aiden-yanzy/hotboard/main/docker-compose.yml
curl -fsSL  https://raw.githubusercontent.com/aiden-yanzy/hotboard/main/.env.example -o .env
```

### 3. 改 .env 三处，然后起

```bash
vi .env
#   HOTBOARD_DATA_DIR=/data/hotboard     ← 数据目录（**不能放 700 权限的 home 下**）
#   POSTGRES_PASSWORD=<换成强密码>
#   SITE_URL=https://你的域名
#   （备案号/广告/友链也在这里，留空则不渲染）
#   SITE_* 改完只需 restart 容器，**不用重新构建镜像**：
#     docker compose up -d --force-recreate web

docker compose up -d
docker compose logs -f collector      # 首轮自动建表 + 灌 69 个源，看到 "源成功 xx" 就成了
```

打开 `http://<服务器IP>:6600` 就能看到站点。**数据库初始化是全自动的**：
采集器 `--loop` 的第一轮会跑 `init_schema` + `bootstrap_sources` + 分类/排序种子（全部幂等）。

### 4. 接域名（可选）

在里面套一层 Nginx/Caddy 反代 `127.0.0.1:6600` 即可，参考下面「部署踩坑记录 → 静态资源缓存 / gzip」。

### 5. 升级到新版本

```bash
cd /opt/hotboard
# 改 .env 里的 HOTBOARD_TAG=sha-xxxxxxx 或 v1.2.3（见 GHCR 包页面）
docker compose pull && docker compose up -d
```

### 6. 镜像地址与可见性

```
ghcr.io/aiden-yanzy/hotboard/web:latest        429MB
ghcr.io/aiden-yanzy/hotboard/api:latest        207MB
ghcr.io/aiden-yanzy/hotboard/collector:latest  167MB
```

三个包都是 **public，可匿名拉取**，不需要 `docker login`。

> ⚠️ 踩过的坑：GitHub 容器包的**可见性在创建时确定**，之后改仓库可见性不会跟着变。
> 最初仓库是私有时创建的 `hotboard-api` / `hotboard-collector` 两个包一直是私有，
> 匿名 pull 会 401。改用**嵌套包名**（`hotboard/web` 这种）新建一套即可自动继承公开可见性。
> 所以新增镜像别用 `hotboard-xxx` 平铺命名，统一放在 `hotboard/` 命名空间下。

## 二、从源码构建（开发者 / 改代码时）

```bash
git clone https://github.com/aiden-yanzy/hotboard.git && cd hotboard
cp .env.example .env && vi .env
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

`docker-compose.build.yml` 只是给三个服务补上 `build:` 段，生产的
`docker-compose.yml` 只认 GHCR 镜像，两者可以并存。

### CI 设计（**别改回 QEMU 一步到位**）

`.github/workflows/docker.yml` 分两阶段：

1. **build**：3 服务 × 2 架构，`amd64` 用 `ubuntu-latest`、`arm64` 用 `ubuntu-24.04-arm`，
   各自**原生**构建，推 `-amd64` / `-arm64` 后缀 tag
2. **merge**：`docker buildx imagetools create` 把两个 digest 合成多架构 manifest，
   产出正式 tag（`latest` / `sha-xxxxxxx` / `v1.2.3`）

为什么不用 `platforms: linux/amd64,linux/arm64` 一步到位：arm64 要在 x86 runner 上走
QEMU 模拟，web 是 Node 项目（`npm ci` 装 sharp 等原生模块），**实测跑了 59 分钟仍未结束**，
只能取消。换原生 ARM runner 后 web 的 arm64 镜像 1 分多钟就构建完。

- 触发：push 到 `main`（文档改动除外）、打 tag `v*`、手动 dispatch
- 缓存：`type=gha`，按 `服务名-架构` 分 scope

## 三、云服务器细节（选型 / 目录 / 初始化）

### 1. 选型

| 项 | 建议 | 说明 |
|---|---|---|
| 配置 | **2C4G** 起（4C8G 更稳） | 4 个容器：PG 最吃内存，其余都很轻 |
| 磁盘 | **40G+** | 库会随快照增长（每轮快照插一行/条），留出备份空间 |
| 系统 | Ubuntu 22.04/24.04 LTS | Docker 官方源支持好 |
| 地区 | **境内**（要 ICP 备案）或境外（免备案但访问慢/不稳定） | 公开运营境内必须备案 |
| 出网 | 允许访问源站（知乎/微博/各媒体网站） | 采集出网 |

### 2. 上传项目 & 配置（源码部署方式，用镜像部署可跳过）

```bash
sudo mkdir -p /opt/hotboard /data/hotboard && sudo chown -R $USER /opt/hotboard /data/hotboard
# 上传：本机执行  rsync -avz --exclude node_modules --exclude dist ~/Projects/hotboard/ 用户@服务器:/opt/hotboard/
cd /opt/hotboard
cp .env.example .env
vi .env
```

云端 `.env` 要点：

```ini
HOTBOARD_DATA_DIR=/data/hotboard          # ← 只改这一处，数据全在这里
HOTBOARD_WEB_PORT=6600
POSTGRES_PASSWORD=<强密码>
TZ=Asia/Shanghai
# 采集：容器内常驻自跑（不用外部 cron）
COLLECT_CMD=--loop --interval 1800
# 采集引擎：自研适配器模式，两个外部引擎都停用
ENGINE_DAILYHOT_URL=
ENGINE_NEWSNOW_URL=
ENGINE_WHITELIST=custom
```

**站名 / 域名 / 备案号 / 友链 / 广告位不在这里配**，改
`apps/web-astro/src/config/site.ts`（改完要重新 build web 镜像）。

### 4. 起栈

```bash
make up && make health
```

首次起来库是空的 → 初始化（建表 + 源清单 + 分类种子，一条命令全做）：

```bash
# ① 建表 + 灌入 68 个源 + 应用分类种子
docker compose exec collector python collect.py --bootstrap

# ② 立刻跑一轮，马上有数据（不跑就要等 30 分钟后的第一轮循环）
docker compose exec collector python collect.py

# ③ 验证
docker compose exec db psql -U hotboard -d hotboard -c \
  "select count(*) as 源 from sources; select count(*) as 条目 from items;"
```

预期：`sources` ≈ 68 行、`items` 数千行。前端刷新即可看到数据。

> ⚠️ `--bootstrap` 是幂等的，重复跑不会重复插源；但 `COLLECT_CMD=--loop` **不会**自动建表，
> 所以全新部署必须先手动跑一次 `--bootstrap`。

### 5. 域名 / HTTPS / 备案

1. **域名解析**：`A` 记录 → 服务器公网 IP（`your-domain.com`、`www`）。
2. **备案（境内）**：服务器厂商备案系统提交（域名 + 服务器都要）；站点有内容运营，如实填写；
   备案号填到 `apps/web-astro/src/config/site.ts` 的 `icp` / `police` 字段后重新构建 web 镜像。
3. **HTTPS**：两种都行 ——
   * **边缘 Nginx/Caddy（推荐）**：容器仍只监听 `6600`，外面用 Nginx 反代 + Let's Encrypt：
     ```nginx
     server {
       listen 443 ssl http2;
       server_name your-domain.com;
       # ssl_certificate ... (certbot 自动)
       location / { proxy_pass http://127.0.0.1:6600; proxy_set_header Host $host; }
     }
     ```
     Caddy 更省事：`your-domain.com { reverse_proxy 127.0.0.1:6600 }`（自动签证书）。
   * **直接暴露**：把 `.env` 的 `HOTBOARD_WEB_PORT` 改成 `80`，自己在 web 容器里配证书（不推荐）。
4. **安全组/防火墙**：只放行 22/80/443；**不要把 5433/6688/6700/4444/6600 暴露到公网**
   （compose 里这些端口默认只绑 `127.0.0.1`，就是为了这个）。

### 6. 备份

```bash
make backup            # 导出到 $HOTBOARD_DATA_DIR/backups/hotboard-日期.sql.gz
```

建议加一条 crontab（每日 03:30，保留 7 天）：

```cron
30 3 * * * cd /opt/hotboard && make backup >/dev/null 2>&1 && find /data/hotboard/backups -name '*.sql.gz' -mtime +7 -delete
```

## 三、从本机迁到云上

1. 云端按上面 1–4 起好栈（先别跑采集）。
2. 本机停写并打包数据：
   ```bash
   cd ~/Projects/hotboard && docker compose stop collector
   make backup            # 或直接打包整个数据目录（含 pgdata，最省事）
   tar czf hotboard-data.tar.gz -C ~/Data/docker-volumes hotboard
   ```
3. 上传 → 云端解包到 `/data/`（覆盖 `pgdata/`）→ `docker compose restart db api web`。
4. 验证：`make health`、前端 `:6600`、`/api/health` 里 `unique_sources` 数量与迁移前一致。

> 用 `pg_dump` 备份 + 空库恢复更干净（跨大版本升级尤其如此）；直接搬 `pgdata` 目录仅限同版本（16）。

## 四、回滚

* **服务级**：`make down` → 改回配置 → `make up`（数据不丢，都在 `HOTBOARD_DATA_DIR`）。
* **数据级**：`gunzip -c backups/hotboard-*.sql.gz | docker compose exec -T db psql -U hotboard -d hotboard`。
* **本机历史形态**：本机迁移前的老容器（`hotdb`/`hotapi`/`dailyhot-api`/`newsnow`）目录与镜像都保留，
  需要时 `docker compose -f ~/Docker/hotdb/docker-compose.yml up -d` 起回来；Caddy 的 `:6600` 段
  在 `~/Docker/caddy/Caddyfile` 里以注释形式保留，取消注释并 `--force-recreate` 即恢复。

## 五、常见问题

| 现象 | 原因 / 处理 |
|---|---|
| 前端打开是旧版、改了不生效 | 前端是**构建期注入**的：改了 `site.ts` 或源码要 `docker compose build web && docker compose up -d web`，别只 restart |
| 分类栏 / 热点推荐是空的 | 分类种子没应用：`docker compose exec collector python collect.py --seed-categories` |
| 全新部署后一条数据都没有 | 没跑初始化：`docker compose exec collector python collect.py --bootstrap`，再跑一轮采集 |
| 端口被占（6600 等） | `lsof -nP -iTCP:6600 -sTCP:LISTEN` 查占用；改 `.env` 的 `HOTBOARD_WEB_PORT` |
| 采集一个源都没有 | 看 `collector-logs/collect-*.log`；确认 `.env` 里 `ENGINE_WHITELIST=custom` |
| 内存不足 / 容器被 OOM kill | 只起必要服务：`docker compose up -d db api web collector`（engine / newsnow 可不起） |
| 切数据源很慢（秒级） | 物化表 `current_items` 没数据：`docker compose exec collector python collect.py` 跑一轮会自动维护 |

## 六、部署踩坑记录（实测）

云上从零部署时踩过的问题，写在这里省得重踩：

### 1. 数据库反复重启：`could not write to file "postmaster.pid": Operation not permitted`

**两个独立原因，都要满足：**

* **数据目录属主必须是镜像内 postgres 用户的 UID**
  * `postgres:16`（debian）→ **999**
  * `postgres:16-alpine` → **70**
  ```bash
  chown -R 999:999 $HOTBOARD_DATA_DIR/pgdata && chmod 700 $HOTBOARD_DATA_DIR/pgdata
  ```

* **数据目录不能放在 `chmod 700` 的父目录下**
  典型：`/home/<用户>/...`，如果该用户目录是 `700`，容器内 UID 999/70 穿不进去，
  即使 pgdata 自身权限正确也会 `Operation not permitted`。
  → 数据目录放到 `/opt/hotboard-data`、`/data/hotboard` 这类父目录是 `755` 的位置。

**另外**：compose 里已经给 db 加了 `user: "999:999"`，跳过官方 entrypoint 的 `gosu` 降权流程
（部分老内核上 gosu 降权后写数据目录仍会失败）。此时就必须配合 `postgres:16`（UID 999）；
如果换回 alpine 版，要同步改成 `user: "70:70"` 并把目录属主改成 70。

### 2. 源列表全空：`sources` 表 0 行

`config.yml` 的 `bootstrap:` 段只列了外部引擎（dailyhot / newsnow）的源，
而实际跑的是自研适配器（`engine='custom'`）。
`bootstrap_sources()` 现在会**自动扫描 `adapters/` 目录**补齐，无需手工维护清单。

### 3. 详情页 404（`/zhihu` 等），列表页正常

`SLUG_TO_SOURCE` 里写的是短名（`"知乎"`），而适配器 `NAME` 是展示名（`"知乎热榜"`），
两者不一致 → 页面判定「源不存在」→ 404。
现在 `SLUG_TO_SOURCE` 由 `adapters/*.py` 的 `SRC_ID` / `NAME` 生成，严格一致。
**新增源后要同步这张表。**

### 4. 适配器加载报 `SyntaxError: source code string cannot contain null bytes`

macOS 打包上传时把 AppleDouble 元数据文件（`._zhihu.py` 之类）也带进去了。
上传前后清理：

```bash
find . -name '._*' -type f -exec rm -f {} +
```

`.gitignore` 已加 `._*`。

### 5. 静态资源缓存（重要，影响手机上「图标慢慢出来」）

`@astrojs/node` 对 `public/` 下的文件默认下发 `Cache-Control: public, max-age=0`，
浏览器每次打开页面都要为几十个源图标逐个回源验证 → 手机上看起来就是图标一个个慢慢出现。
Astro 的 middleware **管不到静态文件**（adapter 直接返回），必须在**前置反代**上加：

```nginx
# 放在站点配置里，优先级高于 location ^~ /
location ^~ /logo/ {
    proxy_pass http://127.0.0.1:6600;
    proxy_set_header Host $host;
    proxy_hide_header Cache-Control;      # 去掉上游的 max-age=0
    add_header Cache-Control "public, max-age=31536000, immutable";
}
location ^~ /ico/  { ...同上... }
location ^~ /_astro/ { ...同上... }   # 构建产物文件名带 hash，可永久缓存
```

Caddy 等价写法：

```
@static path /logo/* /ico/* /_astro/*
header @static Cache-Control "public, max-age=31536000, immutable"
```

### 6. 接口 JSON 必须开 gzip（**最容易漏，手机上切换数据源慢的主因**）

nginx 默认的 `gzip_types` **不包含 `application/json`**。1Panel / 宝塔的默认
`nginx.conf` 只列了 `text/plain application/javascript text/css application/xml`，
所以 HTML 有压缩、接口 JSON 却是明文直传。

实测（Chrome 限速 CPU÷4 + 4G 100ms 延迟 / 180KB/s）单次切数据源：

| | 原始体积 | gzip 后 | 点击→列表更新 |
|---|---|---|---|
| `/api/board?source=微博热搜` | 29.5KB | **5.5KB** | 1075ms → **260ms** |
| `/api/board?source=百度热搜` | 41.8KB | **14.2KB** | 1597ms → **373ms** |

耗时拆解证明瓶颈就在这段下载上：

```
点击 → 列表更新：1075ms
  └─ API 请求 1057ms
       ├─ 等 TTFB  100ms   （正常，就是网络往返）
       └─ 下载     956ms   ← transferSize 29872 = decodedBodySize 29572，完全没压缩
```

在**前置反代**加一个 `gzip <站点>/proxy/gzip-json.conf`（仓库里 `deploy/openresty/gzip-json.conf`
可直接用）。注意该文件被 `include .../proxy/*.conf` 在 **server 层**加载，
所以这里的 `gzip_types` 会覆盖全局列表，要把常用类型一并列出：

```nginx
gzip            on;
gzip_vary       on;
gzip_proxied    any;
gzip_min_length 512;
gzip_comp_level 5;
gzip_types application/json application/javascript text/css text/plain
           application/xml application/xhtml+xml image/svg+xml;
```

改完 `nginx -t && nginx -s reload`，验证：

```bash
curl -sI -H 'Accept-Encoding: gzip' 'https://<域名>/api/board?source=微博热搜' | grep -i content-encoding
# 期望：Content-Encoding: gzip
```

> 如果用的是 1Panel，站点文件在容器里，但 `/www` 已挂载到宿主机
> `/opt/1panel/apps/openresty/openresty/www/`，改宿主机那份才会持久化。

### 7. 汇总：一次切数据源的全部优化点

按贡献排序，都是实测出来的：

| 优化 | 位置 | 效果 |
|---|---|---|
| 接口 JSON 开 gzip | 前置反代 | 29–42KB → **5–14KB**，切源 1.0–1.6s → 0.26–0.37s |
| 响应瘦身 `slim.ts` | `src/lib/slim.ts` | 去掉 `mobileUrl`（与 `url` 100% 重复）、`firstSeen`/`engine`/`timestamp`（前端 0 引用），42KB → 24KB |
| 预取复用同一请求 | `HotBoard.vue` 的 `fetchBoard()` | 点击时预取还在飞 → 原来**再发一次**（手机双倍流量）；改为 await 同一个 Promise |
| `touchstart` 预取 | `HotBoard.vue` | 手机上比 `focus` 早 50–100ms 开始拉数据 |
| 缩略图换 `_l` 后缀 | `apps/api` 的 `clean_cover()` | 单张 86–610KB → **3–20KB**；一页 8.3MB → 522KB |
| 列表 `:key` 带源名 | `HotBoard.vue` | 切源时重建节点，上一批图片请求被取消，不再和下一批抢带宽 |
| 图床 preconnect | `Base.astro` | 少 2–3 个 RTT 的 DNS+TLS 握手 |

### 8. 从部署机访问不到的数据源

部分源从国内服务器**根本抓不到**，留着只会让前端列出一堆空榜单：

| 源 | 原因 |
|---|---|
| V2EX / NodeSeek / Hacker News / 纽约时报 | 境外站，国内服务器 8s 超时 |
| 吾爱破解 | IP 级 WAF 封禁（`reason:UrlACL`，连首页都 403） |
| 酷安 | API 需要 App 签名 token |
| FreeBuf | 阿里云 WAF JS 挑战页 |

处理方式：写进 `jobs/collector/config.yml` 的 `disabled_sources`，采集器每轮会把这些源
`enabled=false`（前端不再列出）。换到能出境的机器后删掉对应行即可自动恢复。

### 9. 源清单与分类：**唯一来源是 `adapters/`，不要在别处维护**

新部署最容易踩的坑，全部集中在「源清单 / 分类」这两件事上，这里一次说清。

#### 9.1 源清单只有一个来源

```
jobs/collector/adapters/*.py     ← 唯一权威：一个文件一个源
        ↓  bootstrap 自动扫描（SRC_ID / NAME / CATEGORY）
   sources 表（engine='custom'）
```

`config.yml` 里原本还有个 `bootstrap:` 段，列着 dailyhot 31 个 + newsnow 30 个源。
**这两个外部引擎早已移除**，但那段清单一直留着 —— 新库跑一次 `--bootstrap` 就会
照单插进 61 行「从未成功、0 数据」的残留，把分类统计撑虚（"综合"从 12 变成 43）。

现在已经删掉那段清单，并加了双保险：

- `bootstrap_sources()` **只处理 `ENGINE_WHITELIST` 内的引擎**，段里若再出现别的引擎只打印警告
- `--bootstrap` 会自动跑 `prune_legacy_engines()`，删掉「非白名单引擎 + 0 采集 + 从未成功 + 无引用数据」的残留行

所以新部署不会再产生这类脏数据；老库升级时跑一次 `--bootstrap` 也会自愈。

> 要加源 → 往 `adapters/` 加一个 `.py`（写上 `SRC_ID` / `NAME` / `CATEGORY` / `fetch()`），
> 重启 collector 即可。**不要**改 `config.yml` 的 `bootstrap:`，也不要手工 INSERT。

#### 9.2 分类也只有一个来源

分类写死在每个适配器模块的 `CATEGORY` 常量里：

```
综合 16 / 娱乐 16 / 科技 11 / 开发 11 / 社区 9 / 财经 5 / 购物 1
```

改分类的正确姿势：**改适配器文件 → 重启 collector**（`bootstrap_sources()` 用
`on conflict (id) do update set name, category` 会同步到库）。

曾经踩过两个坑，都已修掉：

| 坑 | 后果 | 现在 |
|---|---|---|
| `bootstrap` 用 `on conflict (id) do nothing` | 改适配器分类，线上老库纹丝不动，改了等于没改 | 改 upsert，重启即同步 |
| `sql/seed_categories.sql` 按 `name` 匹配 | custom 行的 `name` 是中文展示名（`src_id='cls'` / `name='财联社电报'`），拿英文 id 匹配**零命中**，这份"分类种子"形同虚设 | 改为按 `engine='custom' and src_id in (...)` 匹配 |

也正因为这两点叠加，线上曾出现「**财经分类只有 1 个源**」（只有适配器自带财经的同花顺，
财联社/金十/华尔街见闻/雪球全被归到"综合"）。修完后财经是 5 个源。

#### 9.3 `sources` 表结构约束

```sql
-- 同一引擎内 src_id 必须唯一（2026-11-06 新增）
create unique index if not exists uq_sources_engine_src on sources (engine, src_id);
```

原来只有主键 `id` 约束，同一个源换个 `name` 就能再插一行 —— 历史上就是这么攒出
61 行 `dailyhot:*` / `newsnow:*` 残留的。

#### 9.4 自查命令

```bash
# 引擎分布（正常应该只有 custom 一行）
docker exec hotboard-db psql -U hotboard -d hotboard -c \
  "select engine, count(*) from sources group by 1 order by 2 desc;"

# 分类分布（前端实际展示的源数量）
docker exec hotboard-db psql -U hotboard -d hotboard -c \
  "select coalesce(category,'(空)'), count(*) filter (where enabled)
     from sources where engine='custom' group by 1 order by 2 desc;"

# 有没有「从未成功」的源（排查空榜单）
docker exec hotboard-db psql -U hotboard -d hotboard -c \
  "select src_id, name, last_err from sources
    where engine='custom' and enabled and last_ok_at is null;"
```
